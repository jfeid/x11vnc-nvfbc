# H.264 output

With `-h264`, x11vnc sends the screen as an H.264 video stream while the
screen is moving, and returns to normal Tight encoding when it stops. The video
is encoded on the GPU by NVENC, and clients receive it as RFB encoding 50, the
open H.264 encoding that TigerVNC supports.

This page is the readable summary. The full engineering log, with every
measurement, wrong turn and code reference, is
[`NVENC-H264-PLAN.md`](NVENC-H264-PLAN.md). It is written as working notes for
whoever changes this code next (people or coding agents), not as an
introduction.

## Why

Tight works well for a still desktop: it only sends the parts that changed,
and it keeps full colour detail, so text stays sharp. It breaks down under
motion. Scrolling a page or playing a video changes most of the screen every
frame, and Tight then needs about 26 MB/s at 2560x1440, which is more than
most network links can carry, while using a full CPU core.

A video codec is built for exactly that case. Under the same motion, H.264
needs about 0.4 MB/s.

## How it works

**Tight when still, H.264 when moving.** The server measures how much of the
screen changes per second, using the change map NVFBC already provides. When
more than a set amount changes (`-h264_enter`, in screens per second) it
switches that client to H.264. When the screen calms down (`-h264_exit`) it
switches back and repaints everything with Tight, so text you stop to read is
crisp again. Typing and cursor blinking never trigger the switch.

Both encodings can be mixed on one connection; the client handles each
rectangle by its own encoding. In practice the switch isn't visible, and
scrolling looks cleaner than with Tight, which can tear mid-scroll.

**Only for clients that asked for it.** TigerVNC lists H.264 among its
supported encodings even when the user hasn't selected it, so the server uses
H.264 only for a client that put it first, which is what selecting H.264 as the
preferred encoding in the viewer does. `-h264_force` overrides this.

**The screen is split into bands.** TigerVNC's Windows viewer can't display
an H.264 rectangle larger than about 2.36 million pixels (2048x1152). It
doesn't report an error; it just shows nothing. So the server splits the
screen into horizontal bands under that size, each with its own encoder. A
2560x1440 screen becomes two 2560x720 bands. See
[Known limitations](#known-limitations).

**The server sends only as fast as the client can show.** After each frame
the server asks the client to confirm it (an RFB "fence") and waits for that
before sending the next one. Without it, a slow client falls further and
further behind. With it, the frame rate adjusts by itself: against a Windows
TigerVNC viewer at 2560x1440 it settles at about 12 frames per second. If a
confirmation doesn't arrive within 500 ms, the server sends anyway, so a lost
reply can't freeze the picture.

**No extra copies.** While every client is on H.264, the encoders read the
NVFBC capture buffer directly, and x11vnc skips copying the screen into its
own framebuffer. When the last client leaves H.264, the framebuffer is refilled
before Tight repaints.

**One GPU context for all bands.** By default, the video library creates a
separate CUDA context for each encoder, and each context runs a driver thread
that polls the GPU thousands of times a second. The server creates one context
and shares it between all bands, which removed a third of the CPU cost.

## Results

Measured at 2560x1440 against a real TigerVNC client. `full` is a benchmark
that redraws the whole screen continuously; `medium` redraws a 960x540 area,
which is closer to ordinary use.

| | Tight only | with `-h264` |
|---|---|---|
| network, whole screen moving | 25.8 MB/s | ~0.4 MB/s |

CPU of the whole x11vnc process, with `-h264`:

| scenario | i7-3770 | Ryzen 9 9900X |
|---|---|---|
| idle (benchmark draws nothing) | 11.7% | 9.1% |
| medium | 33.0% | 9.2% |
| full | 72.8% | 28.6% |

100% is one CPU core. The `full` figure is inflated by the benchmark itself:
it keeps the GPU busy, and the driver's polling thread costs more the longer
it waits for the GPU. During ordinary desktop motion that thread costs about
1%.

The raw data is in [`bench/results/`](bench/results/), described in
[`bench/results/NOTES.md`](bench/results/NOTES.md).

## Options

| option | default | meaning |
|---|---|---|
| `-h264` | off | enable H.264 output. Available in builds with NVFBC support; with `-nvfbc` the encoders read the capture buffer directly |
| `-h264_enter N` | 3 | switch to H.264 above N screens/s of change. **8** works better in practice: a video in a quarter of the screen stays on Tight |
| `-h264_exit N` | 0.75 | switch back below N screens/s |
| `-h264_bitrate K` | 20000 | bitrate cap in kbit/s. Actual use is usually far below it |
| `-h264_fps N` | 30 | upper limit on frames per second. The client's confirmations usually set a lower rate |
| `-h264_force` | off | use H.264 for every client that supports it, even if not preferred |
| `-h264_nofence` | off | disable the confirm-before-next-frame flow control |
| `-h264_fence_timeout MS` | 500 | send anyway if the client hasn't confirmed within this time |
| `-h264_tile_pixels N` | 2359296 | maximum band size. Set by the client's limit, not a quality setting |
| `-h264_preset`, `-h264_tune`, `-h264_cq` | p4, ll, off | encoder settings. Tested and none of them improve picture quality (see below) |
| `-h264_cuda_sched MODE` | blocking | `auto` gives each encoder its own CUDA context (the slower default of the video library) |

`-h264_enter`, `-h264_exit`, `-h264_bitrate` and `-h264_fps` can be changed
on a running server, for example `x11vnc -R h264_enter:8`. This only works
when a single x11vnc is running on the display.

## Known limitations

**Text is slightly soft while moving.** H.264 as decoded by TigerVNC keeps
colour at half resolution (4:2:0), while Tight keeps it in full. The
difference shows on coloured text such as syntax highlighting. Higher bitrate
or other encoder settings don't help; this was measured. Full-colour H.264
(4:4:4) exists, but the Windows viewer can't decode it. The switch back to
Tight when motion stops is the mitigation: text is soft only while it's moving.

**TigerVNC's Windows viewer shows nothing for large H.264 rectangles.**
Anything above 2048x1152 pixels stays black, with no error on either side.
The viewer's decoder allocates its output buffer before it knows the video
size and never enlarges it. The band splitting above works around it. A
viewer with a lower limit would show the same silent black area, and the RFB
protocol gives the server no way to find out. Reported upstream: *(link to be
added)*.

**Tested with one client.** All testing used TigerVNC 1.16.2 on Windows. The
Linux build of TigerVNC decodes H.264 with a different library and should
work, but hasn't been tried.

**One driver thread remains.** The shared CUDA context still has one NVIDIA
driver thread that polls while the GPU is busy. It can only be removed by
using the NVENC SDK directly instead of libavcodec, which isn't planned.

## Findings that apply beyond this project

- TigerVNC's Windows viewer silently fails to display H.264 rectangles above
  about 2.36 million pixels.
- The viewer also requires every H.264 frame to start with the SPS (the
  stream's parameter header). Anything before it, even an access-unit
  delimiter, gives a black rectangle and no error.
- NVENC through libavcodec defaults `forced-idr` to off, so a requested
  keyframe is not a real restart point. A fresh decoder can't start from it.
- Strict constant bitrate pads every frame with filler data up to the target
  size. Capped variable bitrate cut the average frame from 500 KB to 34 KB.
- libavcodec creates one CUDA context per encoder, each with its own polling
  driver thread, so CPU cost grows with the number of encoders rather than the
  frame rate. `CU_CTX_SCHED_BLOCKING_SYNC` doesn't change that thread's
  behaviour; sharing one context does.
- A lenient decoder (ffmpeg) accepting a stream proves little about a strict
  one (Media Foundation). Test against the real client early:
  [`bench/h264serve.py`](bench/h264serve.py) serves a pre-encoded file
  as encoding 50 with no x11vnc involved, and it found the size limit within
  minutes after days of looking at the server.
